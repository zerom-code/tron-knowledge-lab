# Knowledge Base → RAG → AI Agent

Версия 3.1.0. Реализованный Python-прототип для тестового Roman Horbachov.

~~~mermaid
flowchart LR
    Article[Статья: текст + URL] --> API[Python / FastAPI]
    API --> Worker[Python ingestion worker]
    Worker --> KB[Knowledge Base: документы и связи]
    KB --> DB[(PostgreSQL + pgvector)]
    Query[Вопрос + metadata] --> RAG[Python RAG Service]
    DB --> Vector[pgvector cosine search]
    DB --> FTS[PostgreSQL Full-Text / ts_rank_cd]
    Vector --> RRF[RRF]
    FTS --> RRF
    RRF --> Rank[OpenAI reranker]
    Rank --> Context[Context Builder]
    Context --> Gate{Достаточно evidence?}
    Gate -->|Да| Agent[AI Agent через OpenAI]
    Agent --> Review[Проверка цитат и каждого абзаца]
    Review --> Answer[Ответ с источниками]
    Gate -->|Нет| Low[Low Confidence: отказ и действия]
~~~

## Различие компонентов

Knowledge Base — модель знаний и их связей. PostgreSQL — СУБД,
в которой модель хранится. pgvector — расширение этой СУБД для векторов.
Embedding — числовое представление текста в определённом пространстве.
RAG ищет релевантные знания и собирает контекст.
AI Agent получает ограниченный контекст и инструкцию для ответа.
Он не получает всю KB, прямой доступ к SQL или ключ через браузер.
В этом сценарии Agent — Python-сервис вокруг структурированных вызовов
OpenAI. Это один агент ответа, а не весь набор агентов на Agents SDK из V1.

## Данные и происхождение

Project → Article → Version → Section → Chunk.
Assertion (Fact/Claim) ↔ AssertionEvidence → Chunk + Source.
Assertions и chunks связываются с entities; assertion относится к topic.
Evidence-связи начальных фактов — альтернативные подтверждения:
каждая должна поддерживать весь факт. Составные утверждения, которые
требуют нескольких фрагментов одновременно, нужно разделять на отдельные факты.
Source хранит URL, тип, время и hash. Версия хранит исходный текст
и его hash; chunk — input hash, модель embedding и vector(256).

Четыре первоначальных документа содержат 22 настоящие выдержки
и восемь вручную сверенных фактов. JSON используется только для
первоначального наполнения; рабочие изменения хранятся в PostgreSQL.
Источник может быть сохранённым снимком страницы или текстом,
предоставленным редактором. Наличие URL не означает автоматический crawl.
Даты показывают получение снимка, а не доказанную дату обновления сайта.

## Обработка

Queued → Parsing → Sections → Chunks → Claims/Entities → Embeddings → Processed.
Статусы и ошибки jobs сохраняются в БД. Worker получает job через
FOR UPDATE SKIP LOCKED. Retry сохраняет Article, создаёт новую Version.
Переключение текущей версии происходит после успешного завершения.
Предыдущая успешная версия остаётся доступной при сбое новой.
Остановленная job возвращается в очередь; после аварийного завершения
истёкшая lease позволяет восстановить обработку.

Парсер очищает HTML, выделяет абзацы/заголовки и ограничивает работу
двенадцатью chunks. Entities выделяются правилами для предметной области.
Выдержки становятся Unverified claims, не «доказанными» фактами.
Редактор сверяет текст с источником, оставляет комментарий и меняет статус.
Проверка происхождения не гарантирует актуальную цену или отсутствие
конфликтов в источниках.

Embeddings новых текстов рассчитывает OpenAI. Для точного совпадения
input hash и модели может использоваться сохранённый вектор.
Имитации embedding нет.

## Retrieval

Python применяет правила понимания запроса и нормализации терминов.
Language/source/topic/entity/document/date/verification и project tpe
ограничивают ОДНУ функцию SQL-фильтрации для обоих поисковых путей.
В поиск идут только live-документы и текущие Processed версии.

pgvector выполняет cosine search; PostgreSQL FTS использует GIN,
to_tsquery и ts_rank_cd. Native FTS не является BM25.
Берётся до 20 кандидатов каждого вида. Python объединяет IDs и складывает
ранги: RRF = Σ 1/(60 + rank). Несопоставимые исходные score не складываются.
OpenAI оценивает до 20 объединённых кандидатов и покрытие вопроса.
SearchRun сохраняет metadata, текст, версии, score и ранги.

HNSW и GIN индексы созданы. На маленьком корпусе PostgreSQL может выбрать
последовательное сканирование. Для большой базы нужно отдельно измерить
recall при ANN и фильтрах, включая iterative scan/over-fetch.

## Контекст и confidence

Клиент передаёт run_id и выбранные IDs. Python проверяет актуальную
версию, статус, фильтры и evidence по PostgreSQL заново.
Пакет: выбранные chunks → подкреплённые facts → их источники → confidence.
Максимум шесть Verified chunks и 7 800 символов их текста.
Tokens показываются приблизительно; это не настоящий tokenizer.

Политика: минимум два chunks с rerank ≥0.70, два поддержанных факта,
источник и coverage вопроса. Confidence означает достаточность evidence,
не вероятность истинности. Порог требует калибровки на контрольных вопросах.
При нехватке сведений генерация блокируется. Для точной будущей комиссии
в источниках нет прогноза, поэтому модель не должна его придумывать.

## Ответ

OpenAI возвращает JSON: абзацы, chunk_ids, limitations.
Сервер проверяет допустимые ссылки и отдельно оценивает каждый абзац
только по его собственным источникам. Возможна одна исправленная генерация.
После повторного отказа показывается ошибка проверки, без выдуманного ответа.
AnswerRun сохраняет итог и входной пакет. Повтор по тому же пакету может
вернуть ранее сохранённый результат с признаком reused.

Два явно различимых режима:

- Saved: три сохранённых результата OpenAI.
  PostgreSQL поиск и Python контекст пересчитываются; embedding вопроса,
  reranker scores и ответ сохранены. Для новых IDs нет фиктивных оценок.
- Live: новый embedding, reranking, ответ и evidence review через OpenAI.
  Ошибка провайдера не маскируется старым ответом.

## Запуск и границы

Один FastAPI backend с раздельными модулями repository/ingestion/rag/context/agent.
SQLAlchemy async + asyncpg, Alembic migrations, PostgreSQL/pgvector.
HTML/CSS/JavaScript отвечают только за представление и вызовы Python API.
Docker Compose поднимает приложение и БД; данные сохраняет Docker volume.
Redis для этого небольшого pipeline не нужен: очередь jobs хранится в PostgreSQL.

Пароль EDITOR_TOKEN защищает импорт, проверку и изменение индекса.
Просмотр и поиск доступны без редакторского пароля. Ключ OpenAI серверный.
Атомарные суточные лимиты ограничивают расход. За туннелем без доверенного
прокси visitor-limit может быть общим для нескольких посетителей.
Прототип однопроектный; это не полный multitenant RBAC.

Не реализуются GSC/GA4/Ahrefs, CMS publication, полный crawler, n8n и весь V1:
в данном задании требуется один сценарий KB → RAG → Agent.
